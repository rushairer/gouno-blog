# Release E2E evidence — 2026-08-24

This record covers the isolated release-candidate verification for the Blog,
Gosso, and Gosso Admin source branches. It is evidence for the release review,
not a statement about production infrastructure.

## Environment

- Compose project: `gouno-release-e2e-hffvay`
- HTTPS endpoint: `https://localhost:18443`
- Application images: built from the current release branches
- Third-party images: the stable `version@sha256` values in
  `release-manifest-v1.1.0.md`
- External AI, email delivery, and production services: not invoked

The project used its own containers, network, database volume, and media volume.
The pre-existing `sso-blog-*` resources remained running and were not modified.

## Passed checks

- Gosso health, readiness, OIDC discovery, and JWKS routes.
- Password login in Cookie Session mode. Access and refresh tokens were absent
  from JSON responses; access, refresh, and CSRF cookie attributes matched the
  release policy.
- Session lookup, refresh, logout, and post-logout rejection of the revoked
  session. Missing and incorrect CSRF tokens returned 403.
- Authorization Code + PKCE for both `gosso-admin-spa` and `blog-spa`, with
  exact registered callbacks. Unregistered and scheme-relative callbacks were
  rejected without an attacker-controlled `Location` header.
- Exact credentialed CORS for the configured application origin. Unlisted and
  similar-name origins received no credentialed CORS headers.
- Administrator access succeeded; a newly created ordinary account was denied
  Gosso and Blog administrative APIs.
- MFA authenticated status and malformed Passkey completion rejection paths.
- Blog media upload rejected unsupported content and an 11 MiB body. A valid
  image submitted with a traversal-style filename was stored under a random,
  path-safe media URL.
- Provider configuration rejected loopback, link-local metadata, and private
  Compose-DNS targets. Targeted provider/link-client tests also passed for
  unsafe ranges, loopback dialing, and hostname/literal-IP address policy.
- Blog, Admin, API, and error responses included the required transport and
  browser security headers. Blog CSP remains report-only by the planned rollout
  policy; Admin CSP is enforced.
- The canonical `/api/v1/auth/login` route returned 429 on the isolated rate
  limit test.
- Final Compose logs contained no tested password, API-key value, email, or
  token JSON fields after the seed warning was redacted.

## Coverage boundaries

- The in-app browser rejected the one-day self-signed localhost certificate
  with `ERR_CERT_AUTHORITY_INVALID`. No browser dependency was installed as a
  workaround. Rendered page loading was therefore verified over HTTP/TLS and
  the SDK storage/origin behavior remains covered by the `gosso-client` test
  suite rather than this browser session.
- No real upstream provider was contacted. Redirect handling and DNS address
  revalidation are supported by code review and targeted tests; this run did
  not exercise a public DNS rebinding service or a real public-to-private
  redirect.
- Results do not cover production reverse proxies, cloud permissions, DNS,
  third-party service configuration, or browser trust-store policy.

## Cleanup

`docker compose down -v --remove-orphans` removed every container, network, and
volume labelled for `gouno-release-e2e-hffvay`. Post-cleanup label queries
returned zero resources. Temporary source copies, certificates, cookies, and
response artifacts were moved to Trash. The pre-existing `sso-blog-*` resource
statuses were unchanged.

## Trusted development stack verification

After the isolated run, the user explicitly authorized rebuilding the existing
development stack with:

```bash
docker compose -f docker-compose.yml -f docker-compose.source.yml up -d --build
```

This run consumed the final `main` images produced from Gosso merge commit
`7edf11d1cc5b219f4d1dcc940889f02cf2ec74ab` and Gosso Admin merge commit
`484c18649c4bd545cdc71c77e66660bc21b61588`, while building the Blog source
branch locally. The relevant immutable `main` manifest digests were:

- Gosso: `sha256:521cfa48dc07a4342fd5be233892d7b819e61bf70d7bea353fed39cc345c41cf`
- Admin seed: `sha256:e09f4b428c7825c801221f7867617ce109d0930bfb00d19a3d61eaeb2aa0d084`
- Admin frontend: `sha256:95513d7d96236202343364a8e721bfa8b2e013bd2ff90349aa0474232a0693e1`

The trusted localhost certificate allowed a real browser check at
`https://localhost:8443`: the Blog home rendered without console errors, the
identity login completed Authorization Code + PKCE for `blog-spa`, and the
browser reached `/admin/dashboard` with administrative data and no console
errors.

Direct HTTP assertions then passed for health/readiness/discovery, exact CORS,
Cookie Session attributes and token-free JSON, refresh CSRF, unregistered OAuth
callbacks, administrator authorization, security headers, malformed Passkey,
unsupported and oversized uploads, and loopback/link-local/internal-DNS SSRF
targets. A Blog-audience PKCE token (`aud=["blog-spa"]`) was used for the Blog
API checks. A traversal-style upload filename produced a path-safe `/media/`
URL, and the created asset was deleted successfully.

The valid upload initially exposed an upgrade defect: the existing named media
volume was not writable by the hardened non-root image. The release branch now
uses a fixed backend UID/GID (`10001:10001`) plus a one-shot, capability-limited
volume initializer. After rebuilding, the initializer exited 0, the resident
backend reported UID/GID 10001, the upload returned 201, and cleanup returned
200. No host-directory permission was loosened.

Unlike the isolated project, this user-authorized development environment was
intentionally left running. Temporary OAuth, cookie, upload, and response
artifacts were moved to Trash; the test-created media database row and file
were deleted.
