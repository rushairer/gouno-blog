# Workflow execution lifecycle

The repository-root AGENTS.md remains authoritative. Preserve the Agent claim, approval, usage, and Provider no-replay boundaries.

- Only a worker with an acknowledged queued-to-running claim may execute or attempt finalization. A losing or uncertain claim must not change Run state, notify failure, or dispatch work. No automatic reclaim or reset.
- Completion is conditional on the Run still being running and must acknowledge exactly one affected row. Cancellation, terminal states and externally transitioned waiting states must not be overwritten by a late worker.
- Bound completion/failure writes to five seconds independently of worker cancellation. Never turn an uncertain completion acknowledgement into a second failure write. Notify failure only after a confirmed failure transition.
- Startup and periodic recovery may drain only queued runs. Never bulk-reset running runs to queued: another replica can still own the claim, and a crash can follow a committed step effect before its checkpoint. A stranded claimed run requires independent operator outcome verification before explicit recovery. The queued scan is not evidence of per-step replay safety.
- Test duplicate claims, committed-before-acknowledgement-loss, before/after completion faults and stale completion with migrated PostgreSQL. These guards do not prove that cancellation interrupts an already dispatched Provider request, that step effects are atomic with checkpoints, or that operator retries are replay-safe.

- Missing checkpoint rows and failed checkpoint reads are distinct. A failed read, malformed stored output, existing non-successful same-run checkpoint, or unconfirmed checkpoint insert stops that execution path; a conflict/no-op is not acknowledgement. Do not dispatch based on unconfirmed evidence or turn it into a retryable failed run. An unconfirmed interaction creation or pending-state query also preserves the claimed run for inspection. ForEach must propagate evidence faults even with continue_on_error; independently executing siblings may already have effects. This is not per-step effect/checkpoint atomicity or permission to replay historical runs.

- A Workflow model step must acknowledge a new queued child Agent run with matching Agent, Workflow run and Workflow version identities before invoking it. Observe the same child identity after execution; missing, mismatched, queued or running outcomes and unknown admission/read failures are unconfirmed evidence, not retryable failed checkpoints or partial batch success. Known typed admission rejections and confirmed terminal child failures keep their existing diagnostic behavior; neither proves external replay safety. Do not infer completion from the worker returning.

- Explicit failed-iteration retry admission must derive the ForEach parent from the source run's exact immutable Workflow version, not the currently selected definition. Verify version ownership and preserve the deleted-Workflow denial. A renamed or moved parent in a newer version must never widen the selected iterations of the old run. This does not certify replay safety of other steps or external effects.

- A duplicate scheduled admission returns the persisted Run and leaves its version, input, resources, checkpoints, terminal status and usage unchanged. Never requeue a failed schedule slot or reset its counters in place; failure does not prove the absence of external effects. A newly scheduled slot remains a distinct Run. Explicit partial iteration retry is a separate contract.

- Each acknowledged Workflow completion reports incremental observed tokens for that claim, not lifetime totals. Add them to persisted run counters in the same guarded status transition; cached checkpoints add no usage and a zero-work resume must not erase previous observations. Reject negative deltas. This covers acknowledged completion phases, not unconfirmed or failed phases, and is not upstream billing reconciliation.

- Serialize explicit retry admission per source Run under its existing row lock and reject any additional retry while a direct retry is queued, running, waiting for user or awaiting approval, even for disjoint iteration selections. This is an active admission guard, not a durable replay ledger: terminal/deleted retries, retry descendants, unrelated Runs and already dispatched external effects are not certified safe by it.

- Confirmed Workflow failure transitions must also atomically add only the current claim's observed usage, retaining earlier phases and rejecting negative deltas. A losing, cancelled, or uncertain transition never authorizes a second write or notification. Unconfirmed execution evidence still prevents finalization; these counters are not a reconciliation ledger for upstream billing or unconfirmed phases.

- Partial iteration retries are admitted only for one isolated top-level ForEach with continue_on_error, pure outer output/approval gates and copied resource-query checkpoints. Its body may contain pure output/approval gates or a sole model step; never replay unrelated batches, outer model/human-interaction steps, nested batches or successful model siblings. Recheck persisted retry metadata and immutable graph before execution, including historical queued retries; missing query checkpoints or out-of-range selections are unconfirmed evidence, not permission to query live resources or widen the batch. Selected failed model replay, terminal retries and billing remain separate concerns.

- ForEach workers must stop assigning new iterations once an unconfirmed execution/checkpoint outcome is published to the batch admission lock. Drain already assigned siblings and preserve their observed usage; never manufacture results or a successful batch checkpoint for unassigned iterations. This is a local dispatch fence, not cancellation or rollback of in-flight Provider or Tool effects. Ordinary confirmed per-item failures retain existing continue-on-error semantics.

- A partial retry consumes the selected source iteration indices at admission, atomically with the retry Run and its snapshots. Keep this minimal ledger independently of retry Run deletion; reject overlaps regardless of terminal status and reject retry descendants, while preserving non-overlapping admissions after the active retry finishes. Backfill only extant retry history; previously deleted retries cannot be reconstructed. No admission record proves external execution, billing, or replay safety. Do not reset consumed indices after cancellation, error, or unknown outcome.

- A retry claim must acknowledge exact ownership of every selected ledger index by that retry Run before dispatch. Preserve owner IDs independently of retry deletion. Historical overlaps or missing owners remain consumed but unowned; never choose a winner by timestamp or status, and never infer authorization after another retry is deleted. Unique extant history can be bound during upgrade, but previously deleted history cannot be reconstructed. A failed ownership check or read leaves the claimed Run for inspection without finalization or replay.
