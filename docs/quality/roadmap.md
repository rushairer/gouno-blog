## 长期边界

执行前阅读根目录 `AGENTS.md`，以及与任务相关的架构、设计和贡献文档。

- 保留独立域 confidential BFF；浏览器不得获得原始 Provider Token。
- 本地身份与权限、近期 MFA、刷新/注销竞争和审计边界不得降级。
- 本地 HTTPS 使用 `blog.dev.local` / `sso.dev.local` 的标准 443 端口，禁止使用 8443。
- 开发镜像遵守 main/local 通道，生产遵守显式镜像与 Secret 文件契约。
- Connector 处于设计冻结期；本路线图不授权其行为、路由、迁移或工作区改造，也不增加业务事件向其自动投递。
- 沿用项目 SemVer 与 CHANGELOG 约定；质量工作不自动触发版本升级、镜像发布或生产部署。
- 默认采用模块化单体。新框架、微服务、共享组件包或大规模目录搬迁必须有具体收益证据。

文档与实现发生冲突时，先对照根规则、测试和当前公共契约记录差异；不能仅因历史文档不同就修改安全行为。产品决策未定的工作保留决策点，不阻塞无关任务。

## 执行与交接约定

1. 每个任务开始记录实际分支、HEAD 和工作区状态，核实问题仍存在。基线不是永久事实。
2. 默认串行，一项任务形成可独立审核的变更。使用 `codex/*` 分支或隔离 worktree；保留用户改动，不 reset、不覆盖。
3. 新会话不会自动继承聊天历史，以本目录、当前代码和提交为事实来源。
4. 若使用新 worktree，必须确认本计划和前置改动存在于其起点；不要从未包含计划的远端分支直接启动。未提交计划只能在拥有这些文件的工作区读取。
5. 任务卡依次使用 `planned → in_progress → implemented → verified → integrated`；`blocked` 必须写明具体缺失条件。实现完成、验收通过和集成完成分别记录。
6. 后续任务依赖的变更必须已在其基线中。不要仅凭前一会话说“完成”就开始。
7. 做范围内必要修复与测试；额外发现记入待办，不顺手展开。生产部署、发布和跨仓契约变更不由通用任务提示词自动授权。
8. 完成后更新任务卡的结果区和本表状态，记录命令、退出状态、跳过项、提交/PR（如有）、剩余风险与下一步。
9. 自测后审核实际 diff。每阶段另开验收任务，复核证据；验收发现的非琐碎问题回到原任务或新修复卡处理。

前置计划及 Q01/Q01a 已包含于 `codex/q01-ci` 的 `c1c6158`。Q01b 修复和当前状态更新尚未提交。Q02 必须在包含这些工作区改动的基线上执行；其他 worktree 不能仅检出该 HEAD 就认为前置齐全。没有执行推送或创建 PR。

## 后续任务的细化要求

### Q05：安全与身份验证

建立控制—实现—测试矩阵，覆盖 BFF 回调/注销重放、刷新与注销竞争、MFA freshness、角色/资源越权、SSRF、媒体主动内容、审批重放和工具范围。优先补缺失验证，按已证实问题做最小修复。检查 `doc/auth-client-boundary.md` 中 transport API、CSRF 命名、后台门禁说明与实现的差异，不能把差异直接定性为漏洞。

区分 miniredis 单测与真实 Redis 多实例/并发验证。沿用现有安全包目标：Auth BFF 80%、Provider 75%、Secretbox 85%，按同口径覆盖率逐步提高门槛；不能以百分比代替竞争、拒绝和重放场景。涉及 GoSSO/SDK 变化时另列跨仓任务、兼容矩阵和回归，不盲目升级到仓库最新版本。

### Q06–Q08：公开内容体验

Q06 检查列表 DTO 的所有消费者（含站内 AI 工具），避免删除全文字段破坏隐含依赖。使用固定文章数量和长度的测试数据，对比 API 原始/压缩响应量、首屏请求和资源；不得把构建包大小当作 LCP。

Q07 比较预渲染、后端 HTML 输出和其他必要候选，明确发布/定时发布后的更新时效、缓存失效、删除/404、草稿隔离、站点设置、容器和维护成本。先做一个公开文章路由的验证，再由用户确定方案。后台保持现有认证边界，不预设全站迁移到新框架。

Q08 验证不执行 JS 也有文章标题、摘要、canonical/分享元信息；确认不存在内容的 HTTP 状态；更新、撤回、删除及站点配置变更均不会泄漏草稿或长期展示旧数据。

### Q09：代码复杂度

以状态和职责划分编辑器及工作流模块，先列出待保留行为和测试。保持协议、权限、预算、审批和工作流资源快照语义。每个 PR 处理一个职责边界。行数只作为导航信号，不设置“低于某行数即合格”的机械目标。不为拆分而引入大量透传接口。

### Q10：设计语言

建立组件样例与关键页面截图基线，逐步把历史覆盖归回 Token、组件或页面；兼容规则有删除条件。验证明暗主题、窄屏、缩放、长文本、键盘、焦点恢复、加载/失败/空状态及减少动态效果设置。跨项目先明确 Token/交互契约，是否提取包由真实复用成本决定。Connector 不属于本轮可修改界面。

### Q11：运维与贡献

先盘点现有能力，再补请求/运行关联、错误和延迟、队列/工作流失败等最小信号，避免日志泄露凭据与敏感数据。在隔离环境完成数据库和媒体恢复，并验证与加密密钥管理的配合。记录可实测 RPO/RTO、步骤和时间；阈值按实际运营需求确认，不虚构业务要求。使用干净环境复现贡献文档，修复不存在的脚本或过时指令。

## A+ 验收门槛

| 维度 | 必须有的证据 |
| --- | --- |
| 正确性 | 发布、撤回、编辑冲突、权限拒绝、审批等关键成功与失败路径可重复验证 |
| 安全 | 高风险控制有拒绝/重放/竞争验证；不存在已确认且未解决的高危问题；扫描与人工审阅范围明确 |
| CI | 干净环境可执行；必需数据库测试不跳过；格式、类型、UI/CSS 与相关检查进入真实门禁 |
| 架构 | 关键模块职责、状态和事务边界可解释；改动有聚焦测试；重要决策有 ADR |
| 前端体验 | 元信息、草稿保留、错误恢复、移动端、明暗主题和键盘操作有证据 |
| 性能 | 固定数据、设备和网络条件下建立公开页/API 基线与预算并验证；未测速不能宣称达标 |
| 运维与协作 | 独立环境恢复成功、可追踪故障、贡献者可从文档跑通必要验证 |

最终复评应区分“达到”“未达到”“未验证”。覆盖率和平均分不能抵消关键安全、数据完整性或恢复方面的缺口。非核心低风险未完成项可明确列出，但不能靠降低门槛宣称 A+。
