# Q02：文章并发编辑保护

状态：planned。前置：Q01 的测试设施已进入当前工作基线；记录其提交或其他可核对 diff。

## 目标与范围

两个编辑者从同一版本修改文章时，后保存者得到明确冲突；其草稿保留，不发生静默覆盖。覆盖数据库、文章 API、前端编辑器和已有其他文章写入入口的兼容性。

阅读 PostRepository、PostService、PostController、文章请求/响应类型、`src/api/posts.ts`、PostEditor、OpenAPI、版本恢复及 AI 内容写入调用。Connector 不在范围内。

## 实施步骤

1. 复核当前保存链路，列出人工编辑、版本恢复、批量状态、定时发布、AI 审批等实际写入者及版本策略。不是所有计数变化都应触发编辑冲突，先明确版本代表内容/发布状态还是整行。
2. 设计显式 revision 或等价协议，记录旧客户端缺失版本的行为。受保护编辑不能因缺失版本自动降级为无条件覆盖。若需改变公共契约，提供清楚兼容/迁移说明，不擅自扩大到 SDK 升级。
3. 新增 additive migration，初始化旧数据；不修改已有历史迁移。验证干净安装和旧 schema 升级。
4. 数据库以 expected revision 做原子条件更新并递增。不能先 SELECT 比较再无条件 UPDATE。区分不存在、无权限和版本冲突，冲突时不得产生成功审计或多余业务副作用。
5. 前端携带读取版本；收到 409 保留所有未保存字段，提供明确提示和安全的查看最新/重新加载路径。丢弃草稿需要明确用户动作，不自动重试覆盖；首版无需实现自动三方合并。
6. 保留现有作者/角色与资源权限检查。所有实际写入者按约定递增或校验版本，避免恢复或 AI 写入使保护失效；超出可控范围时拆子任务并记录依赖。

## 验收

- [ ] 两个客户端读取相同 revision，第一个保存成功，第二个 409，数据库保持第一个内容。
- [ ] 真正并发的同版本提交只允许一个成功，由数据库集成测试证明。
- [ ] 同一编辑器连续保存可使用新 revision 正常成功。
- [ ] 缺失/非法 revision、不存在文章、未授权用户行为符合明确契约。
- [ ] 冲突后正文、标题、分类、标签及其他编辑字段没有被自动替换或清空。
- [ ] 主动加载最新内容与退出冲突提示有清楚的交互和草稿保护。
- [ ] 恢复、发布及其他现有写入入口符合版本策略；覆盖相应回归。
- [ ] 新安装和已有文章数据升级通过；API 类型/OpenAPI/用户影响说明同步。
- [ ] 后端相关集成/race/vet、前端质量检查通过；使用本地标准 HTTPS 做双页面保存交互验证。

## 交付与取舍

交付一个完整行为闭环。记录选定的并发协议及缺失版本策略。若操作人/权限/敏感操作边界需要新产品决策，先完成无争议验证再明确提出，不借并发保护重写认证。
